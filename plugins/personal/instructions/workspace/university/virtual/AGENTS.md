# Отчёты по технологиям виртуализации

Эти правила дополняют общий университетский профиль из родительского `AGENTS.md` для работ в выбранной папке.

Локальные ресурсы `{{REPORT_BUILDER}}`, `{{REPORT_REQUIREMENTS}}` и `{{STYLE_TEMPLATE}}` настраиваются при подключении профиля. Генератор, требования и Word-шаблон не входят в плагин. Если нужное значение не задано или файла нет, остановись и запроси ресурс; не подменяй его придуманным файлом или стилями.

## Результат

- У каждой работы должен быть один канонический Markdown и один одноимённый DOCX рядом с ним.
- Не создавай версии `final`, `v2`, `preview` и другие дубликаты, если пользователь не запросил их явно.
- Титульный лист не создавай и не заполняй: пользователь вставляет его самостоятельно. DOCX начинается с оглавления.
- Итоговая структура берётся из `{{REPORT_REQUIREMENTS}}`: оглавление, цель работы, ход работы, вывод, ответы на вопросы и список использованной литературы.

## Исходные материалы

- Прочитай PDF задания через соседний Markdown с тем же именем. Если Markdown отсутствует, создай его с помощью `file-to-markdown` и проверь полноту конвертации.
- Если готового текста выполнения нет, составь краткий ход работы по заданию и фактам пользователя. Не придумывай команды, результаты, адреса, измерения и выполненные проверки.
- Вопросы бери из PDF задания. Отвечай кратко и по существу; недостающие технические сведения сверяй с первичными или официальными источниками.
- Скриншоты не открывай и не анализируй без прямой просьбы. Их количество, смысл и порядок определяются описанием пользователя.

## Канонический Markdown

Используй следующую иерархию и точные названия основных разделов:

```markdown
# ОГЛАВЛЕНИЕ

1. Цель работы
2. Ход работы
3. Вывод
4. Ответы на вопросы к практической работе
5. Список использованной литературы

# ЦЕЛЬ РАБОТЫ

# ХОД РАБОТЫ

## Название этапа

# ВЫВОД

# ОТВЕТЫ НА ВОПРОСЫ К ПРАКТИЧЕСКОЙ РАБОТЕ

1. **Текст вопроса?**  
   Краткий ответ.

# СПИСОК ИСПОЛЬЗОВАННОЙ ЛИТЕРАТУРЫ
```

- Для каждого будущего скриншота добавляй ровно один отдельный абзац:

```text
ВСТАВЬ СЮДА ИЗОБРАЖЕНИЕ ПРО КРАТКОЕ ОПИСАНИЕ СКРИНШОТА
```

- Сохраняй формулировку плейсхолдера дословно. Не добавляй номер рисунка, подпись, пояснение, рамку, таблицу или фон, если пользователь этого не попросил.
- Количество плейсхолдеров должно точно совпадать с количеством названных пользователем скриншотов.
- В списке литературы оставляй 2–3 внешних источника. Само задание и PDF практической в этот список не включай.

## Генерация DOCX

- Используй только настроенный общий `{{REPORT_BUILDER}}`; не создавай отдельный генератор для каждой работы.
- Генератор обязан загружать `{{STYLE_TEMPLATE}}`. Не используй пустой `Document()` и не воспроизводи шрифты вручную.
- Семантические стили шаблона обязательны: `P: Заголовок 1 уровня`, `P: Заголовок 2 уровня`, `P: Мой основной текст`, `P: Список`, `ИСТОЧНИКИ`, `Иллюстрация`, `TOC Heading`, `toc 1`.
- Плейсхолдер изображения должен быть обычным абзацем стиля `Иллюстрация`. Таблицы разрешены только для настоящих табличных данных.
- Пример запуска после подстановки локального пути к генератору:

```bash
python3 "{{REPORT_BUILDER}}" "<канонический-источник.md>"
```

- Для новых работ действует стандартный допуск критика из родительского `AGENTS.md`. Не добавляй общий флаг обхода проверки. Если пользователь явно отменил критика для конкретной работы, ограничь исключение только точным путём этой работы.

## Проверка

- Перед генерацией проверь наличие всех обязательных разделов, 2–3 источников и точное число плейсхолдеров.
- После генерации убедись, что нет титульника, таблиц вместо изображений, старых служебных меток и самовольных подписей.
- Проверь структурно, что каждый плейсхолдер имеет стиль `Иллюстрация`, а заголовки и основной текст используют стили шаблона.
- Для контроля текста скопируй итоговый DOCX во временный файл с другим именем, преобразуй его в Markdown и сравни с каноническим источником. Временные файлы после проверки удали.
